  Manual/Aperture-Priorityの2択しか持たずシャッター優先モードが無く、かつオートが選ぶ

  `camera_perception.launch.py` が `v4l2_camera` 起動の3秒後に

### T-27-6 / T-27-5-6 — YOLO-World は色をほぼ無視する（色検証フィルタで補う）

- **YOLO-World は色をほぼ無視する（confidenceでは色の誤認識を区別できない）**（T-27-6, 2026-07-13実機発見）: テキストクエリ`"blue toy car"`に対し、実機で赤いおもちゃの車がconf 0.9超（青い車自身より高スコア）でマッチした。`min_confidence`をいくら上げても解決しない（暗所では本物の対象もconf 0.5台に留まるため、閾値を上げるとむしろ本物を取りこぼす）。対策として検出後の色検証フィルタ `color_verification_logic.py`（ROS2非依存）を追加: `extract_color_keyword()`が英語ターゲット文字列から色キーワードを抽出、`color_match_ratio()`が検出bbox内HSV画像のうち目標色相に一致する有効画素（彩度・明度が一定以上）の割合を返す。`yoloworld_worker_main.py._yolo_step()`はconfidence降順の候補を順に見て色検証も通る最初の1件を採用する（`color_verify`パラメータ、既定True）。bboxは物体の正確な輪郭マスクではなく矩形のため、対象物のすぐ隣・背景に別の色の物体があるとそのピクセルが混入し誤ってPASSしうる問題（実機で「赤い箱＋隣接する青いおもちゃの山」を誤検出）に対し、`crop_center_fraction()`（`color_verification_logic.py`）でbbox中心寄り（既定`color_verify_crop_fraction=0.65`）だけを色検証対象に絞る対策を追加済み（T-27-5-6、2026-07-17実装・実機で誤検出なしを確認）。「隣室到達」を含めた再検証は`todo/ai_core.md` T-27-5-7が未了。`min_confidence`は現在0.4（低confidenceノイズ除去程度）。

### T-29 — `yolo` 追従の検出には自前のフレーム間トラッカーが入っている

- **`yolo` 追従の検出には自前のフレーム間トラッカーが入っている**（`object_tracker_logic.py`、T-29、2026-07-17）: 検出源の Isaac ROS `YoloV8DecoderNode` は純粋なデコーダでトラッカーを持たず `vision_msgs/Detection2D.id` を一度も埋めないため、`ObjectTrackingLogic.select_target()` のIDロックオン機構（`/target_id`）は実装済みにもかかわらず**入力が来ず長らく不動作だった**。`IouTracker`（`object_tracking_info_node` が `_to_detection_inputs()` と `select_target()` の間に挟む）が bbox の IoU 貪欲対応付けでIDを採番してこれを供給する。**対応付けは IoU と class_id のみで行い中身を見ないため class 非依存**（`target_class_ids` が person でも cup でも同じに機能する。人特化の縦横比・面積上限フィルタは方針として却下済み）。
  - パラメータ: `tracker_enabled`（既定 `true`、`false` で従来動作＝ID空・毎フレーム最大面積に戻す）/ `tracker_iou_threshold`（0.3）/ `tracker_min_hits`（3＝3フレーム連続で対応付いて初めて「確定」）/ `tracker_max_age`（10＝対応付かなくても10フレームはID維持）/ `sticky_target`（既定 `true`）。
  - **T-29（棚の物体をpersonとして誤検出）はこれで塞ぐ**: 誤検出は「新規トラック・hits=1」として現れるため `tracker_min_hits` で弾かれる（「棚だから」ではなく「続かないから」＝汎用的）。加えて `sticky_target` により自動選択モードでも一度選んだトラックを追い続けるため、**追従中により大きな別物が現れてもターゲットを奪われない**（`[AUTO: Largest]` の最大面積優先が効くのは初回捕捉時のみになる。ログのラベルも sticky 有効時は `[AUTO: Sticky]` になる）。
  - **限界（重要）**: 外見特徴（ReID）を持たないため、`tracker_max_age` を超える完全オクルージョンを跨いだ同一性は保証しない。**「ロスト → Tier2で探索 → 隣室で再発見」を同一IDで繋ぐことはできない**（再出現時は新IDが振られる）。保証されるのは連続的に見えている間＋短いオクルージョンまで。真の同一人物性が要るなら外見embedding（BoT-SORT+ReID等）が別途必要。
  - 詳細・却下した代替案（Ultralytics `BYTETracker` 流用／decoder差し替え等） → `todo/ai_core.md` T-29
  - **`sticky_target` は「動かない静止物への誤検出固着」には無力だった**（T-29-6a、2026-07-29）: 棚・壁等の静止物を高confidenceで連続hitし続ける誤検出は`tracker_min_hits`を素通りし、一度stickyに選ばれると`is_lost()`も真にならず自力復帰不能な膠着に陥る実機事象が2件発生した（うち1件は距離推定も失敗し完全デッドロック）。`ObjectTrackingLogic`に凍結検知を追加: 正規化bbox面積が`sticky_freeze_area_min`（既定0.45）以上かつ位置・サイズが`sticky_freeze_pos_tol_norm`（既定±2%）以内で不動の状態が`sticky_freeze_timeout_sec`（既定20秒）続いた候補を自動選択の候補から除外する（sticky対象ならreset_sticky相当で自動解除）。判定は壁時計秒（`select_target(..., now=...)`、省略時は常に不発火の後方互換）。凍結中のtrackが動けば即座にアンカーがリセットされ除外は解除され、track自体が途切れて再出現すれば新ID（ReID非搭載のため）で別物扱いになるため、時限クールダウン等の追加状態管理は不要と判断した。明示ロック（`/target_id`）は判定対象外（ユーザー指定を常に尊重）。**`yoloworld`（物体探索）はこのフィルタの対象外**（`object_tracking_info_node`を経由しない別パイプラインであり、そもそも「大面積・接近」は探索の到達目標なので誤検出扱いすると誤動作する）。実機未検証（次回実機セッションでT-29-6b）。詳細 → `todo/ai_core.md` T-29-6 / `todo/logs/ai_core.md` T-29-6節「対策実装」

### T-35 — タレットは検出欠落を「コースト」で吸収する（prime + coast の2点セット）

- **タレット（`turret_tracker_node`/`TurretController`）は検出欠落を「コースト」で吸収する**（T-35、2026-08-05。設計・実装・pytest完了、`colcon test`・実機検証は未実施）: `control_loop` は 20Hz 固定タイマーだが `_latest_pan_error` は `info_cb`（検出到着時）でしか更新されず、YOLO 実測は約10Hz。加えて**1フレームでも検出が捨てられると `target_visible=False` → `SimplePID.reset()` が走り `_prev_error` が 0 に戻る**ため、再捕捉時に対象が動いていなくても `error/dt` という偽の微分インパルス（実ゲイン `pan_kp=100`/`pan_kd=10` で**定常出力のちょうど3倍**）が出ていた。毎回 reset されるため減衰せず、定常誤差0.30のE2Eで「1つおきに検出が欠落」すると連続検出比**136%**まで行き過ぎる（＝行き過ぎ→誤差反転→また行き過ぎの左右振動）。3回に1回まで落ちると95%（追従不足）へ転じるため**「半分落ちる」が最悪点**であり、T-33 が「実在人物の conf は 0.85〜0.94 に集中」と記録している以上 `min_confidence=0.85` はこの最悪点にピンポイントで嵌まる設定値だった。**対策は2点セット**（片方だけでは症状が入れ替わるだけ）: ① **prime**（`SimplePID.prime(error)`）＝差分を取るべき前回値が無い場面（初回捕捉・真のロストからの再捕捉）では `_prev_error` を現在誤差で初期化し微分を0から始める。`detection_coast_sec` の値によらず常に有効。② **coast**（`TurretController` の新パラメータ `detection_coast_sec`、`turret_tracker_node` 既定 **0.2秒**＝20Hz で4tick、`0.0` で無効）＝検出が途切れてもこの秒数までは「まだ見えている」とみなし直近の誤差で追従を継続し reset しない。①だけだと136%の行き過ぎが**55%の追従不足**に置き換わり、ユーザー報告のもう一方の症状（「旋回の方が速くタレットが置いていかれる」）そのものになる。結果、コースト期間内なら検出レートによらず連続検出と同一の追従になり、超えると素直に劣化する（青天井に走り続けない）。コースト中かは `TurretController.is_coasting` で判別できる。**なお閉ループ検証で、P主体（`pan_ki=0`）ゆえの定常追従遅れ（= `omega/pan_kp × 画角半分` = 0.3×omega [deg]、車体60deg/s旋回で画角半分の50%）が別に存在することが判明した。偽インパルスはこの遅れをたまたま打ち消していたため、本修正で挙動を一貫させると遅れが素直に見えるようになる**（退行ではなく露見）。対策はT-36（車体ヨーレートのフィードフォワード）で別途検討。詳細 → `todo/ai_core.md` T-35 / T-36、`todo/logs/ai_core.md#t-35-2026-08-05` / `#t-35b-2026-08-05`

### P4-6 — タレットのサーチスイープは「ロスト直前の方位」を起点に pan から掃引する

- **タレットのサーチスイープは「ロスト直前の方位」を起点に pan から掃引する**（P4-6、2026-08-09デスク。設計・実装・ホストpytest完了、`colcon build`/`colcon test`・実機検証は未実施＝P4-6b）: 旧 `TurretController._run_search()` は固定パターンで、①`search_grace`（1.5秒）経過後まず **tilt を天井方向へ全振り**して `tilt_min` まで戻すため最初の約3.1秒 pan が一切動かず、②その後の pan 掃引方向 `_search_direction` は**追従中に pan が `pan_max-5`/`pan_min+5` に達したときだけ**書き換わる値で、ロスト時に人がどちらへ抜けたかとは**無相関**（実質コイントス）、③最終目撃方位を起点にせず現在 pan から可動端まで振り切るため「最も人が居そうな方位のすぐ隣」が最後に回ってくる。実機既定値での計測では、ロスト後に人の実方位（±10°）を向くまで**有利側5.00秒／不利側15.90秒**かかり、`tier1_timeout_sec`（8.0秒）に対し**不利側の半数は Tier1 の持ち時間中に一度も人の方位を向けない**＝背骨 C-2-1 で従来動作）＝ロスト確定時に `_search_anchor_pan`（最終目撃方位）と `_escape_sign`（直近 `pan_error` の符号＝画角のどちら端から抜けたか。`_search_direction` と違い離脱方向と必ず相関し、誤差がほぼ0のときだけ従来値へフォールバック）を latch し、**pan を逆に振りワールド方位を保持する（追従中は PID が誤差として吸収するため適用しない）。**案C**（新規トピック **`/follow/person_estimate`**、`geometry_msgs/PointStamped`、goal_frame）＝`follow_goal_generator_node` が Tier1 の先回りゴール（`_compute_recovery_goal()` の「最終目撃点＋進行ベクトル延長」で**`dist_offset` を引いていない人物位置の推定そのもの**）を、Tier1 を抜けた後は `search_anchor()` を配信し、`turret_tracker_node` が TF で `turret_base_link` へ落として方位に変換しサーチの起点にする。結果、**4ケースすべて1.80秒に揃いコイントスが消滅**した。**フェーズ番号は従来の1〜3を据え置き優先窓を11〜12の別系統として追加**している（番号を振り直すと既存テストと実機の挙動理解の両方がずれるため）。**案Bの効果は限定的**で、人が静止し車体だけ回る状況の画角内滞在率は 0%→13%（車体90°回転時）にとどまる。**原因はタレット可動域が±80°しかないこと**で、車体が60°以上回ると人の相対方位が可動域外へ出て補償の有無に関係なく物理的に向けない。これはタレット側では解けないため車体側の課題として P4-7 へ分離した。**実装中に自分で作り込んだ欠陥を2件テストが検出**している: ①案Bの補償で `current_pan` ### P4-7 — サーチの「人物推定方位を狙う追尾モード」は実装済みだが既定で無効

- **サーチの「人物推定方位を狙う追尾モード」は実装済みだが既定で無効**（P4-7、2026-08-09デスク。実装・pytest完了、**`anchor_track_max_sec` 既定 `0.0`＝無効で出荷**）: P4-6 の優先窓は「アンカー中心 ±`search_priority_deg`(40°) を掃引する」動きなので、タレットは常に**窓の端**を目指し**アンカー（人物推定方位）そのものは狙わない**（人の推定方位が分かっているのに約40°横を見続ける。計測で t=3.5s のズレ 36.5°）。そのため案C を有効にしても画角内滞在率が1%も改善しなかった。対策として `TurretController` に `_PHASE_ANCHOR_TRACK` と `anchor_track_max_sec` を追加し、推定が生きている間はその方位を直接狙い、予算切れ・推定失効で優先窓→全域スイープへ降りる（全域スイープまで降りたら戻らない＝P4-6 と同じ飢餓防止）ようにした。**ただし既定は無効。** 推定誤差を振った測定で、追尾は「推定が正確である」ことへの賭けであり**30°ずれると車体の動きに関係なく悪化する**（画角内滞在率: 車体回転時 61%→45%、静止時 62%→46%、発見までの時間も +2〜3秒）と判明したため。**優先窓の ±40° 掃引が推定誤差に対する保険として機能しており、追尾はそれを捨てる動きになる**——Tier1 の推定は「最終目撃点＋進行ベクトル延長」なので人が角を曲がれば30°程度は普通にずれる。P4-6 の窓幅は期待される推定誤差とよく釣り合っている。**なお「推定が完璧」という前提だけで測ると予算は長いほど良いという逆の結論が出る**（無制限で100%）。この測定だけで既定を決めていたら退行を出荷していた。有効化は実機で推定精度を測ってから判断する（→ P4-7b、`ros2 param set /turret_tracker_node anchor_track_max_sec 3.0`）。**併せて、起票時の P4-7（「探索中の車体旋回を人物推定方位で制限する」）は取り下げた**: 根拠にした測定が案Bの単独測定で、真因は車体ではなく上記の実装だった。車体90°回転時に人が可動域内にいる時間が5%しかないのは事実だが、車体旋回の制限は Nav2 の経路追従と正面衝突するため C-2-1 撮影前のリスクとして棚上げした。詳細 → `todo/object_tracking_recovery.md` P4-7 / P4-7b、`todo/logs/object_tracking_recovery.md#p4-7-2026-08-09--サーチ中に人物推定方位を狙う追尾モード`

### 距離推定 — follow_goal_generator_node の距離推定優先順位（AI深度 > ToF、ToF は既定 false）

- `follow_goal_generator_node` の距離推定優先順位: **AI深度 > ToF**。ToF は実機で値の信頼性が低いことが確認されたため `use_tof` パラメータで制御（**デフォルト `false`** = 実質 AI深度のみ）。どちらも無効な場合、`estimate_distance()` は `None` を返し `on_timer()` が安全に停止する（ゴールキャンセル・待機）。固定2mフォールバック（旧 Fixed-2m）は「対象を認識しているのに2m先を狙って近づかない」不具合の原因だったため撤去済み（2026-07-05）。BBox高さからの距離推定（旧 YOLO-Est、`use_dynamic_dist`/`dist_k`）は物体サイズの多様性により誤差が大きく撤去済み（2026-07-05）。ロスト時リカバリー（Tier1先回り/Tier2フロンティア探索）の詳細 → `todo/object_tracking_recovery.md`

### N19-9a — 近距離の追従ゴールは「対象より `dist_offset` 手前」を必ず守る

- **近距離の追従ゴールは「対象より `dist_offset` 手前」を必ず守る（N19-9a、2026-08-08デスク。実装・ホストpytest完了、`colcon build`/`colcon test`・実機検証は未実施＝N19-9b）**: `compute_base_goal()`（`distance_estimator.py`）に `max(..., 0.5)` という無条件の下限があり、対象が `dist_offset < dist < dist_offset + 0.5`（既定 **0.5〜1.0m**）にいるとき「ゴールは対象より `dist_offset` 手前」という不変条件を破って**ゴールを対象側へ押し出して**いた。対象自身が LiDAR に映る障害物なので、dist=0.74m ではゴール-対象間が 0.24m まで詰まり `inflation_radius: 0.22`／内接半径 0.15 に対する余裕がほぼ消える（対象は点ではなく幅を持ち、深度推定は bbox 中心を指すため実際の最近傍はさらに手前）。さらに停止判定が `dist <= dist_offset + 0.2`（=0.7m）という**下限 0.5 とは無関係な直書き定数**だったため、その隙間 0.7〜1.0m が「停止もせず、壊れたゴールを送る」穴になっていた。対策は2点: ①下限を 0.0（ゴールが背後に回らないためだけの意味）へ縮小 ②停止判定を新パラメータ `min_goal_advance_m`（既定 **0.25**、Nav2 の `general_goal_checker.xy_goal_tolerance` 0.10 より大きく取る）を使う純関数 `should_stop_for_proximity()` に一本化し、ゴール計算と停止判定が同じ不変条件を共有するようにした（既定値では停止帯が 0.7m → 0.75m へわずかに広がる）。**この修正が説明するのは 0.74〜1.0m 帯だけで、1.0〜1.6m 帯はゴール座標が旧実装と完全に同一**なので別原因（→ N19-9b で切り分け）。**併せて `[FOLLOW] Nav result:` のログを修正**: 旧実装は `SUCCEEDED` 以外を全て `'FAILED/ABORTED/CANCELED'` の1文字列に潰していたが、`continuous` モードは対象が動くたび `cancel_active_goal()`→`send_nav_goal()` するため**正常な追従中も `on_timer` 周期（既定0.5秒）でこの行が出続ける**（キャンセルされたゴールの結果コールバックは後から必ず発火する）。つまり実機で観測された「0.5秒間隔で連発」は本物の `ABORTED` と正常な `CANCELED` の混合で、症状の大きさ自体が測れていなかった。純関数 `nav_result_label(status, superseded)` で実ステータス名を出し、自分で差し替えた古いゴールには `(superseded)` を付ける。詳細・数値検証 → `todo/navigation.md` N19-9 / `todo/logs/navigation.md#n19-9-2026-08-08`

### N19-10a — Tier1 先回りは「Nav2 の結果が返るたび必ず前へ進むか終わる」

- **Tier1 先回りは「Nav2 の結果が返るたび必ず前へ進むか終わる」（N19-10a、2026-08-09デスク。実装・ホストpytest完了、`colcon build`/`colcon test`・実機検証は未実施＝N19-10b）**: `FollowRecoveryLogic.tier1_outcome()` の到達分岐は候補列 `[予測ゴール, 実測点(新), ..., 実測点(最古)]` を `[:_tier1_idx+1]` に刈り込んで `_tier1_idx=0` に戻す設計だが、**`_tier1_idx == 0`（予測ゴールそのものに到達）のときは「いま到達したばかりのゴール」を `_recovery_goal` に再設定**していた。`_on_tier1_nav_result()` が直後に `last_sent_pose=None` として `_send_recovery_goal()` の再送抑止（`min_update_trans` 既定0.20）を解除するため、次の `on_timer`（既定0.5秒）で同一座標を送信 → ロボットは既に `xy_goal_tolerance`(0.10) 内なので Nav2 が即 SUCCEEDED → また再設定、が **`tier1_timeout_sec`（ノード既定8.0秒）を使い切るまで回る**（2026-08-07実機ログの `Pursue goal: x=-0.55, y=-1.91` → `SUCCEEDED` → 同一座標、の連発がこれ）。C-2-1 背骨の④Tier1先回り→⑤Tier2探索の遷移が丸ごと8秒遅れる。**対策1**: 予測ゴール到達時は Tier1 のモデルが尽きたとみなし `_enter_tier2('tier1_predicted_goal_reached')`（残る候補はすべて後退方向＝既に通過した点なので試す価値がない）。遷移先は既存の `tier1_candidates_exhausted` と同じ経路で、`_search_anchor` も従来どおり `candidates[0]`＝到達した予測ゴール＝人が向かった先になる。Tier2 無効時は GIVEUP（旧実装もタイムアウト後に同じ所へ落ちていたので終着点は同じ、空回りが消えるだけ）。**対策2**: `_build_tier1_candidates()` で直前に採用した候補から `min_breadcrumb_dist`（既定0.15、Nav2 の `xy_goal_tolerance` 0.10 より大きい）未満の候補を落とす——対象がほぼ静止したままロストすると `_compute_recovery_goal()` が進行方向を取れず**最新 breadcrumb そのもの**を返すため予測ゴールと最新実測点が同一座標の重複候補になり、Nav2 が失敗したのと同じ点へ「後退」して候補列と持ち時間を捨てていた（同ログの `Pursue goal: x=-0.21, y=0.87` → FAILED → 同座標、がこれ。無限ループではないが症状はログ上同じに見える）。回帰テスト `test_tier1_never_reproposes_the_goal_just_finished` が上記の単調性を直接押さえている。詳細 → `todo/navigation.md` N19-10 / `todo/logs/navigation.md#n19-10-2026-08-09`

### N19-15a — breadcrumb は「人の実測位置」であってゴールではない

- **breadcrumb は「人の実測位置」であってゴールではない（N19-15a、2026-08-09デスク。実装・ホストpytest完了、`colcon build`/`colcon test`・実機検証は未実施＝N19-15b）**: `follow_goal_generator_node` は追従中、Nav2 ゴール（対象より `dist_offset` 手前）とは別に「対象の実測位置」を breadcrumb として記録し、これが **Tier1 先回り（進行方向の外挿）と `trail_follow`（T-27）の共通入力**になる。その記録側にゴール用の `lookahead_distance`（既定 2.2m）が渡っており、コメントが「人の実測位置そのものを記録する」と宣言しているそばから 2.2m でクランプしていた。**症状は「2.2m で頭打ち」より悪い**: クランプ後の点は base_link 基準で**自機から 2.2m** の地点であり、map へ変換されるため**自機が動けばその点も動く**。結果、遠方で観測した区間ほど軌跡が系統的に自機側へ引き寄せられ、人が実際に歩いた形とは違う軌跡が残る（Tier1 の予測ゴールが手前に張り付き、`trail_follow` の standoff 起点もずれる）。**対策**: 記録専用の純関数 `compute_person_position()`（`distance_estimator.py`、ROS2非依存・pytest対象）を新設し `lookahead_distance=math.inf` で呼ぶ。**引数を1つ直すだけにしなかったのは、呼び出し側の引数ミスは純ロジックの pytest では原理的に検出できない**ため（`compute_base_goal()` 自体はどちらの引数でも仕様どおり動く）で、意図を関数名と docstring に固定するのが唯一の歯止めになる。`compute_base_goal()` は無変更＝ゴール側の挙動には一切触れていないので、退行時の切り分けは1軸で済む。**`max_lateral`（既定1.5m）は意図的に据え置き**——距離は AI 深度の直接測定だが、横方向は正規化 `center_error` に線形ゲインを掛けた外挿値で、上限は測定値の切り捨てではなく発散止めとして意味を持つため。ただし `target_dist` が実距離まで伸びたぶん上限が効き始める距離は下がった（旧: `|center_error|`>0.68 でのみ発動 → 新: 8m なら >0.19 で発動）ので実測で確認する（→ N19-16、`@jetson`）。詳細 → `todo/navigation.md` N19-15 / N19-16、`todo/logs/navigation.md#n19-15-2026-08-09`

  **T-33-2 だけでは症状が消えていなかった（T-33-3、2026-08-11デスク。実装・ホストpytest完了、`colcon build`/`colcon test`・実機検証は未実施＝T-33-3b）**: T-33-2 が塞いだのは「タイマーが*同じ*メッセージを読み直す」経路だけで、**「タイマーが*新しい*が中身は非検出のメッセージを読んで数える」経路が残っていた**。`object_tracking_info_node` は対象が写っていないフレームでも `target_visible=False`／`center_error=0.0`／`tracking_id=''` の `ObjectTrackingInfo` を**毎フレーム publish** し（この定常 publish 自体は知覚死活監視 P8-13＝`perception_heartbeat_stale()` が依存しているので止められない）、`_info_seq` は `info_cb` の可視判定より**前**で加算される。`on_timer` の入場条件は `not is_lost()`＝「最後に見えてから `lost_timeout_sec`(1.5秒) 以内」であって「いま見えている」ではないため、**中身が空の新しいフレームが grace に流れ込み、誤検出1フレームの 0.5 秒後（タイマー1tick目）に確定する**——T-33 の症状がそのまま残っていた。しかも非検出フレームは誤差 0.0（悪化にならない）・track_id 空（`prev_track_id and cur_track_id` が偽）なので、T-33／T-33-2 が足した2つの防御は**どちらも原理的に発火しない**。**対策**: `advance_visible_grace()` に `visible` を**必須引数**として追加し、非検出フレームでは状態を一切変えず `confirmed=False` を返す。ノードは `info_cb` が `last_visible_time` を更新するのと同一条件（`target_visible` かつ `confidence >= min_confidence`）を渡す。**非検出フレームでリセットもしない**のが要点で、YOLO は1フレームおきの取りこぼしが起きうる（T-35）ため厳密な連続可視を要求すると本物の再捕捉が永久に確定できなくなる（人が目の前にいるのに探索を続ける真逆の壊れ方）。連続性の上限は既にノード側にある——`is_lost()` が真になれば `on_timer()` が `_recovery_visible` を初期化するので、可視フレームの間隔が 1.5 秒を超えれば streak は自然に切れる。**引数を省略可能（既定 True）にしなかった**のは、本件の本質が「呼び出し側が検出の無いフレームのデータを渡していたこと」であり、呼び出し側の引数ミスは純ロジックの pytest では原理的に検出できないため（N19-15a で `compute_person_position()` を新設したのと同じ理屈で、意図をシグネチャに固定するのが唯一の歯止め）。あわせてノード側のガードを `if in_recovery:` へ広げ、**grace 無効（`recovery_visible_grace_count<=0`）でも非検出フレームでは確定しない**ようにした（従来はここが素通りだった）。詳細 → `todo/ai_core.md` T-33-3 / T-33-3b、`todo/logs/ai_core.md#t-33-3-2026-08-11`

### P8-4 / P8-7〜P8-11 — is_complete() の2種類の停滞判定（ローカル / グローバル）

- `GvdExplorer`/`FrontierExplorer` の `is_complete()` は「候補が完全にゼロ」（`_no_gates_count`/`_no_target_count`）に加え、新規エリアがほぼ増えないケースを検知する2種類の独立した停滞判定を持つ（2026-07-07, P8-4/P8-7/P8-9/P8-10/P8-11）:
  1. **ローカル判定**（`{gvd,frontier}_area_stagnation_limit`＝既定6、`_min_m2`＝既定0.05、`_radius_m`＝既定2.0m）: 直近のクラスタ中心（`_area_stagnation_anchor`）から radius 以内に居座り続けている場合だけ連続カウントし、遠方の新規候補への挑戦は数え直す。「最初にクラッタへはまった場合に他の未探索領域を試す前に探索全体が完了扱いになる」リスクを避けるため。
  2. **グローバル判定**（`{gvd,frontier}_area_stagnation_global_limit`＝既定15、`_global_avg_m2`＝既定0.05）: 場所を問わず直近N件の new_area の移動平均（`deque`）が閾値未満なら完了扱い。「マップ全体に小さな未回収ポケットが点在し、場所を転々としながらもどこも僅かにしか進まない」ケース（ローカル判定は効かない）を捕捉する。
  この2つの停滞トラッキングは `record_outcome()` で **source を問わず**（`gvd_gate` だけでなく `micro`/`opening`/`frontier` も）記録する。GVD の Phase2 Micro フォールバックが同一座標への trivial な「成功」を繰り返すだけで新規エリアが増えないケースは、以前は `source != 'gvd_gate'` の早期 return で停滞検知が完全に無効化されていたバグがあった（P8-8 で発見・P8-11 で修正）。
  また `_handle_giveup()` はロスト継続中に即座に Tier2 へ再突入するケースに備え、探索エンジンの退役記憶（`_tier2_explorer` 等）を破棄しない（`_tier2_reset(preserve_explorer=True)`）。`PatrolExplorer` は事前計算済み固定ウェイポイントを順次消化する方式のためこの種のリスクは無い。詳細・長時間シム検証ログ（3回の実機シム試行の経緯含む）→ `todo/logs/object_tracking_recovery.md` P8-4〜P8-11
  `preserve_explorer=True` は `_interrupt_recovery_if_confirmed()`（対象を再検知して確定するたび呼ばれる）でも使う（T-27-5, 2026-07-13）。以前はここで無条件に `_tier2_explorer` を破棄していたため、対象の見え隠れ（誤検知含む）を繰り返すたびに `PatrolExplorer` の巡回ウェイポイント進行インデックスが失われ、同じ地点への重複到達を繰り返す不具合があった。
  **`preserve_explorer=True` は探索セッションの進行状態（`_tier2_action_index` / `_tier2_nudge_done`）も引き継ぐ**（T-29-5, 2026-07-17）。旧実装はこの2つを `preserve_explorer` によらず常に 0/False へ巻き戻しており、対象の見え隠れのたびに**同じウェイポイントに対してノッジ（前進0.15m＋90度旋回）が再実行**され、ウェイポイントを1つも消化しないままノッジ→再提案→畳まれるを繰り返していた（実機では「同一ウェイポイントでずっと詰まっている」ように見えるが、実体は押す前に畳まれていただけで、誤検出が収まった後は同じ地点を一発で突破した）。ノッジは「ウェイポイント1つにつき1回」（T-AT-6-17 で `_finish_tier2_outcome()` が到達のたび False に戻す）が正しい仕様。

- **背景（2026-09-02）**: 棚卸しの結果、レベルがフィルタとして機能しておらず（毎周期出る `[gvd]` 系まで INFO）、タグは60種超が無規約に混在し（小文字ノード名系・大文字イベント系・台帳ID系・一発物）、OTel Logs(Loki) への配管（`EventLogger`）は完成していたのにアプリノードでの採用率がゼロだった。GUARD の持続ブロック・車輪空転・Nav2 のゴール結果はログ行にしか存在せず Prometheus からは「起きていない」のと区別が付かなかった。
